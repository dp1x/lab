> **Lesson for future graduations:** editing `lab_utils/__init__.py` is not free —
> it invalidates downstream `code_sha256` records. Prefer new submodules. Graduate
> the re-exports only in a provenance-aware change that regenerates dependent result
> artifacts.

### Fourth defect, found during commit preparation — **NOT fixed**, recorded for Task D

`phase0_baseline_breathing.py` records a per-file code fingerprint via
`hashlib.sha256(p.read_bytes())` — i.e. over the **worktree bytes**. This repo has
`core.autocrlf=true` and `.gitattributes` marks only raw `*.txt` snapshots as
`-text`, so `*.py` is stored LF in the blob but checked out CRLF.

Consequence, verified directly:

| Bytes hashed | sha256[:16] |
|---|---|
| `71b2448` blob, LF as stored | `ac673b31cd9fd5be` |
| `71b2448` blob, CRLF (what the worktree actually had) | **`49d20cf9e62de55f`** |
| `phase0_1yr.json` `provenance.code` pin | **`49d20cf9e62de55f`** |
| current worktree file | `646d68f7ecce4097` |
| `phase0_18.6yr.json` `provenance.code` pin | **`646d68f7ecce4097`** |

So the 1-yr artifact is **genuinely** the product of the committed `71b2448` code —
its provenance is sound in substance. But the recorded fingerprint **cannot be
verified from the repository**: anyone checking out the blob and hashing it gets
`ac673b31…`, not `49d20cf9…`. The same will be true of `phase0_18.6yr.json` the moment
this commit lands. A code fingerprint that depends on the contributor's
`core.autocrlf` setting is not a provenance record; it is a platform artifact.

**Not fixed here** because fixing it means re-running campaigns to regenerate
fingerprints, which would touch pre-registered evidence. Task D owns it. Minimum
fix: hash the **blob-normalised** text (`p.read_bytes().replace(b"\r\n", b"\n")`) or
hash a `git hash-object`-equivalent, and add `*.py text eol=lf` to `.gitattributes`
so the worktree and the blob agree.
